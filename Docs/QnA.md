# 최종발표 예상 질문 및 답변

## 1. 프로젝트 전체 방향성

### Q1. 이 프로젝트의 핵심 차별점은 무엇인가요?

**답변:**  
단순히 X-ray 이미지를 분류하거나 처방을 추천하는 개별 기능이 아니라, X-ray 이상 탐지 결과, 환자 진료 데이터, 그래프 기반 처방 이력, LLM 기반 추천, ValidationAgent 검증을 하나의 End-to-End 흐름으로 연결했다는 점입니다. 특히 추천 결과에 confidence_score와 검증 reasoningTrace를 함께 제공하여 의료진이 AI 결과를 설명 가능한 형태로 검토할 수 있도록 설계했습니다.

### Q2. AI가 최종 진단이나 처방을 결정하는 시스템인가요?

**답변:**  
아닙니다. 본 시스템은 의료진의 최종 판단을 대체하지 않고 보조하는 시스템입니다. X-ray 추론 결과와 처방 추천 결과는 참고 정보로 제공되며, 최종 진단과 처방 결정은 의사가 수행합니다. 시스템에서도 ValidationAgent 결과를 모달로 제공하여 의료진이 근거를 확인한 후 판단하도록 구성했습니다.

### Q3. 왜 XAI가 필요하다고 보았나요?

**답변:**  
의료 분야에서는 단순히 “이 처방을 추천한다”는 결과만으로는 신뢰를 얻기 어렵습니다. 추천 결과가 어떤 환자 정보, 상병, 과거 처방 이력, 문헌 근거에 기반하는지 설명할 수 있어야 합니다. 따라서 ArangoDB 그래프 근거, confidence_score, ValidationAgent reasoningTrace를 함께 제공하여 설명 가능성을 높이고자 했습니다.

## 2. 데이터 및 제한사항

### Q4. 실제 의료 영상을 사용하지 못했다면 시스템의 의미가 약한 것 아닌가요?

**답변:**  
실제 의료 영상은 개인정보와 의료 데이터 접근 권한 문제로 사용이 제한되었습니다. 따라서 본 프로젝트에서는 실제 병원 적용 전 단계의 시스템 아키텍처와 워크플로우 구현에 초점을 두었습니다. 즉, 영상 분석 결과가 발생했을 때 이를 상병 추론, 처방 추천, 검증 로직으로 연결하는 구조를 구현하는 것이 핵심 목표였습니다. 실제 임상 데이터가 확보되면 현재 구조에 모델과 데이터를 교체하여 확장할 수 있습니다.

### Q5. 처방 추천 평가 데이터는 실제 임상 데이터인가요?

**답변:**  
처방 추천의 통계 기반 평가는 방문 및 처방 행 단위의 데이터를 Train, Calibration, Test로 나누어 수행했습니다. 반면 에이전트 평가에서는 LLM 생성 시나리오와 템플릿 시나리오를 사용했습니다. 이는 tool 호출 정확도, 답변 품질, hallucination과 같은 LLM Agent 특성을 평가하기 위한 별도 평가 데이터입니다.

### Q6. 데이터셋 규모가 충분하다고 볼 수 있나요?

**답변:**  
현재 규모는 캡스톤 프로젝트 수준에서 시스템 동작과 평가 방법론을 검증하기 위한 규모입니다. Train Set은 746 방문, 5,991 처방 행, Test Set은 161 방문, 1,220 처방 행으로 구성되었습니다. 실제 의료 서비스 수준으로 확장하려면 더 다양한 병원, 질환, 처방 데이터를 추가하여 외부 검증을 수행해야 합니다.

## 3. 시스템 구조 및 기술 선택

### Q7. 왜 MySQL과 ArangoDB를 함께 사용했나요?

**답변:**  
MySQL은 환자 정보, 진료 이력, 사용자, 진단서와 같은 정형 업무 데이터를 저장하는 데 적합합니다. 반면 처방 추천에서는 방문, 상병, 처방 사이의 관계를 탐색해야 하므로 그래프 DB가 더 적합합니다. ArangoDB는 상병-처방 co-occurrence, 유사 환자군 처방 패턴, confidence_score 계산에 필요한 관계 탐색을 위해 사용했습니다.

### Q8. RabbitMQ를 사용한 이유는 무엇인가요?

**답변:**  
ValidationAgent 검증은 X-ray 결과, 상병, 처방, PubMed 근거 검색 등을 포함할 수 있어 시간이 오래 걸릴 수 있습니다. 이를 동기 API로 처리하면 프론트엔드 응답성이 떨어질 수 있습니다. 따라서 Spring Boot가 Validation Job을 RabbitMQ에 발행하고, ValidationAgent가 비동기로 처리하도록 구성했습니다. 프론트엔드는 jobId로 상태를 polling하여 결과를 확인합니다.

### Q9. Redis는 현재 핵심 기능에 사용되나요?

**답변:**  
현재 핵심 데이터 저장은 MySQL과 ArangoDB가 담당하고, Redis는 캐시 또는 세션/임시 데이터 저장을 위한 인프라 구성 요소로 포함했습니다. 향후 추천 결과 캐싱, 세션 관리, LLM 응답 캐시 등으로 확장할 수 있습니다.

### Q10. 왜 AI 서비스를 Spring Boot 안에 넣지 않고 FastAPI로 분리했나요?

**답변:**  
처방 추천, X-ray 분석, 진단서 생성, ValidationAgent는 Python 기반 AI 라이브러리와 LLM 연동이 많습니다. Spring Boot는 업무 API와 트랜잭션 처리에 집중하고, AI 로직은 FastAPI 서비스로 분리하면 모델 교체와 실험이 쉬워집니다. 또한 Docker Compose를 통해 각 서비스를 독립적으로 배포하고 확장할 수 있습니다.

## 4. 처방 추천 및 XAI 신뢰도

### Q11. confidence_score는 어떻게 계산되나요?

**답변:**  
confidence_score는 LLM이 임의로 생성하는 값이 아니라 ArangoDB 기반 그래프 통계와 피드백을 활용해 계산합니다. 동일 상병에서 특정 처방이 얼마나 자주 등장했는지를 나타내는 Frequency Score, 유사 케이스와의 관련성을 나타내는 Similarity Score를 결합합니다. 기본 구조는 `0.7 × s_freq + 0.3 × s_similarity + feedback_adjustment`입니다. 여기에 accepted, rejected, missed 의사 피드백을 반영하여 점수를 보정합니다.

### Q12. LLM이 존재하지 않는 처방을 생성하면 어떻게 처리하나요?

**답변:**  
현재 추천 결과가 DB에 직접 매칭되지 않으면 프론트엔드에서 “처방 상세 선택” 팝업을 통해 `/api/diagnoses` 검색 결과 중 실제 DB 처방을 선택할 수 있도록 구현했습니다. 또한 평가 결과 hallucination rate가 높게 나타났기 때문에 향후에는 프롬프트 제약과 후처리 guard를 강화하여 DB에 없는 처방명과 처방코드가 자동 반영되지 않도록 개선할 계획입니다.

### Q13. 처방 상세 선택 팝업은 왜 필요했나요?

**답변:**  
LLM이 추천한 처방명이 실제 처방 마스터 DB의 명칭이나 코드와 완전히 일치하지 않는 경우가 있습니다. 이 경우 그대로 저장하면 DB 정합성이 깨질 수 있습니다. 따라서 사용자가 추천 처방과 가장 가까운 실제 DB 처방을 검색하고 선택하도록 하여, 최종 저장되는 처방은 반드시 DB에 존재하는 항목이 되도록 보완했습니다.

### Q14. 처방 추천이 상병과 무관한 약을 추천할 가능성은 없나요?

**답변:**  
그 가능성을 줄이기 위해 ArangoDB의 상병-처방 관계와 유사 환자군 처방 패턴을 사용합니다. 또한 ValidationAgent가 저장 상병, 증상, 추천 처방 간 일관성을 추가로 검증합니다. 다만 평가 결과 답변 품질과 hallucination에서 개선 필요성이 확인되었기 때문에, 실제 적용 전에는 처방명/코드 anchoring과 후처리 guard를 더 강화해야 합니다.

## 5. ValidationAgent 및 검증 로직

### Q15. ValidationAgent는 구체적으로 무엇을 검증하나요?

**답변:**  
ValidationAgent는 저장 상병, 저장 처방, 증상, X-ray 추론 결과 간의 일관성을 검증합니다. X-ray Result Loader, Disease Validator, Prescription Validator, Prescription Finder, PubMed Loader를 사용하여 필요한 근거를 수집하고, 최종적으로 overallStatus, summary, reason, reasoningTrace를 반환합니다.

### Q16. ReAct 방식이 꼭 필요했나요?

**답변:**  
검증 과정은 상황에 따라 필요한 도구가 달라집니다. X-ray 결과가 있으면 영상 추론과 상병 일관성을 확인해야 하고, 근거가 부족하면 PubMed 검색이 필요할 수 있습니다. ReAct 방식은 에이전트가 현재 상태를 보고 필요한 tool을 선택하며 reasoningTrace를 남길 수 있다는 장점이 있어 사용했습니다.

### Q17. PubMed 근거는 어느 정도 신뢰할 수 있나요?

**답변:**  
PubMed 근거는 최종 판단 근거라기보다 의료진이 참고할 수 있는 문헌 후보로 제공합니다. 시스템은 논문 제목과 초록 요약을 가져오지만, 최종 판단에서는 의료진이 환자 상태와 원문을 함께 확인해야 합니다. 따라서 보고서와 UI에서도 PubMed는 참고 근거로 표현했습니다.

## 6. X-ray 이미지 분석

### Q18. X-ray 분석 결과가 처방 추천에 직접 반영되나요?

**답변:**  
X-ray 분석 결과는 predictedDiseases와 heatmap 또는 결과 이미지 형태로 저장되고, ValidationAgent의 검증 입력으로 활용됩니다. 즉, X-ray 결과가 바로 처방을 결정하는 것이 아니라, 저장 상병과 영상 추론 결과가 일치하는지 확인하고 처방 추천 검증에 참고하는 구조입니다.

### Q19. X-ray 파이프라인의 단계는 어떻게 구성되나요?

**답변:**  
X-ray 이미지 입력 후 anomaly detection으로 이상 부위를 탐지하고, 해당 영역을 중심으로 masking을 수행합니다. 이후 마스킹된 이미지에서 embedding을 생성하고, Vector DB에서 유사 케이스를 검색합니다. 마지막으로 유사 케이스의 진단 이력을 바탕으로 의심 상병 후보를 도출합니다.

### Q20. 영상 분석 모델의 정확도는 어떻게 검증했나요?

**답변:**  
이번 프로젝트에서는 실제 의료 영상 데이터 접근이 제한되어 영상 모델 자체의 임상 정확도보다는, 영상 분석 결과가 시스템 내에서 어떻게 저장되고 검증 로직에 연결되는지에 초점을 두었습니다. 향후 실제 병원 데이터 또는 공개 벤치마크 데이터셋을 확보하면 모델 성능을 별도로 정량 평가할 계획입니다.

## 7. 성능 평가

### Q21. 처방 추천 정확도에서 Appropriate 78.2%는 어떤 의미인가요?

**답변:**  
Test Set에서 추천 또는 평가된 처방 중 78.2%가 기존 통계 기준상 적정한 처방으로 분류되었다는 의미입니다. 이는 상병-처방 관계 기반 통계 점수가 일정 수준의 구분력을 가진다는 것을 보여줍니다. 다만 이 결과는 통계 기반 적정성 평가이며, LLM 답변 품질 평가는 별도로 수행했습니다.

### Q22. Calibration AUC 0.860은 어떻게 해석하나요?

**답변:**  
AUC 0.860은 적정 처방과 검토 필요 처방을 구분하는 통계 점수의 판별력이 비교적 높다는 의미입니다. 다만 실제 의료 현장에서는 AUC만으로 충분하지 않고, 안전성, 설명 가능성, 의료진 검토 가능성이 함께 고려되어야 합니다.

### Q23. 에이전트 평가에서 hallucination rate가 0.9로 높은데, 큰 문제 아닌가요?

**답변:**  
맞습니다. 이 결과는 현재 시스템의 중요한 개선 지점입니다. 다만 해당 평가는 일부러 sparse data, fake drug, prompt injection 같은 공격적 시나리오를 포함한 stress test입니다. 이 평가를 통해 LLM이 근거 밖 처방명이나 코드를 생성할 수 있다는 위험을 확인했고, 그래서 DB 기반 처방 상세 선택 팝업과 향후 후처리 guard 강화 방향을 도출했습니다.

### Q24. Tool path F1은 높은데 답변 품질은 낮은 이유는 무엇인가요?

**답변:**  
Tool path F1은 DB 조회, 프롬프트 생성, LLM 호출, JSON 파싱 같은 파이프라인 단계가 올바르게 실행되었는지를 봅니다. 반면 답변 품질은 생성된 처방명과 이유가 실제 근거에 잘 연결되는지를 봅니다. 따라서 시스템 흐름은 안정적으로 작동했지만, LLM이 근거를 충분히 반영하지 못한 케이스가 있어 답변 품질 점수가 낮게 나온 것입니다.

## 8. 진단서 생성

### Q25. 진단서 자동 생성은 의료적으로 안전한가요?

**답변:**  
진단서 생성 결과는 자동 확정되지 않고, 의료진이 직접 확인하고 수정할 수 있도록 설계했습니다. 시스템은 초안을 생성하고 PDF 및 DB 저장을 지원하지만, 최종 문안은 의사가 검토한 후 저장하는 구조입니다.

### Q26. 진단서 생성 평가의 entailment rate 79.36%는 무엇을 의미하나요?

**답변:**  
LLM이 생성한 소견이 실제 처방 내용과 의미적으로 일치하거나 함의 관계를 가진 비율입니다. 114건을 대상으로 LLM-as-Judge 평가를 수행했고, 79.36%가 실제 처방과 의미적으로 연결된 것으로 평가되었습니다. 나머지 케이스는 문안 수정이나 프롬프트 개선이 필요한 영역입니다.

## 9. 보안 및 운영

### Q27. 환자 개인정보 보호는 어떻게 고려했나요?

**답변:**  
프로젝트 환경에서는 실제 개인정보를 사용하지 않았고, 시스템 구조상 사용자 인증과 권한 제어를 적용했습니다. Spring Boot에서는 사용자 권한에 따라 접근 가능한 기능을 제한하고, JWT 기반 인증 구조를 구성했습니다. 실제 운영 시에는 데이터 암호화, 접근 로그, 비식별화, 의료정보 관련 법적 요구사항을 추가로 반영해야 합니다.

### Q28. 실제 병원 EMR과 연동하려면 무엇이 더 필요한가요?

**답변:**  
우선 병원 EMR의 데이터 스키마와 API 표준에 맞춘 인터페이스가 필요합니다. 또한 실제 상병/처방 코드 체계와 매핑, 의료 영상 PACS 연동, 개인정보 보호, 감사 로그, 임상 검증 절차가 추가되어야 합니다. 현재 프로젝트는 이 확장을 고려하여 Spring Boot, Python AI 서비스, DB, 메시징을 분리한 구조로 설계했습니다.

### Q29. 실시간성이 충분한가요?

**답변:**  
처방 추천과 검증 과정은 LLM 호출과 외부 API 검색이 포함되어 지연이 발생할 수 있습니다. 이를 줄이기 위해 검증 작업은 RabbitMQ 기반 비동기로 분리했습니다. 사용자는 jobId를 통해 상태를 확인하며, 향후에는 Redis 캐시나 LLM 응답 캐싱을 적용해 반복 요청 지연을 줄일 수 있습니다.

## 10. 개선 방향

### Q30. 가장 먼저 개선해야 할 부분은 무엇인가요?

**답변:**  
가장 우선적으로 개선해야 할 부분은 LLM hallucination 방지입니다. 평가 결과에서 근거 밖 처방명과 처방코드 생성이 확인되었기 때문에, 프롬프트 제약 강화, DB 기반 후처리 guard, 처방 상세 선택 흐름 고도화가 필요합니다. 즉, 모델을 바꾸기보다 실제 DB 근거에 묶인 추천만 허용하는 구조를 강화하는 것이 우선입니다.

### Q31. 향후 연구 방향은 무엇인가요?

**답변:**  
단기적으로는 Agent 추론 정확도 향상, 검증 및 재추천 루프 개선, hallucination guard 강화가 필요합니다. 장기적으로는 다중 질환 처방 추천, 실제 병원 EMR 및 PACS 연동, 실제 임상 데이터 기반 외부 검증을 수행하는 방향으로 확장할 수 있습니다.

### Q32. 이 프로젝트가 실제 의료 현장에 적용되려면 어떤 검증이 필요할까요?

**답변:**  
실제 적용을 위해서는 더 큰 규모의 임상 데이터 검증, 의료진 블라인드 평가, 안전성 검증, 처방 오류 탐지율 평가, 개인정보 보호 검토가 필요합니다. 또한 AI 결과가 실제 진료 의사결정에 어떤 영향을 주는지 전향적 평가가 필요합니다.
