# DR 전략 — "원본 코드 수정" 을 어디서 가르나

2026-09-01

같은 문제를 두 세션이 반대 방향으로 풀었다. 둘 다 같은 실패 모드를 봤고 서로 다른
비용을 골랐다. 이 문서는 **무엇을 "원본 코드 수정" 으로 볼지** 를 정하고, 그 기준으로
둘을 재서 하나를 고른다.

| | PR #38 → 이 브랜치 | PR #40 → `dr/mvp` |
|---|---|---|
| 방식 | 공용 코드에 기능 플래그 | main 에 병합하지 않는 장기 브랜치 |
| main | DR 을 아는 줄이 남는다 | 깨끗하다 |
| DR 이미지 | 프론트·백엔드 각 1개 | 프론트 2개, 백엔드 1개 |
| CI | 매 푸시마다 DR 스택 검증 | 이미지 뽑을 때만 |

---

## 1. "원본 무수정" 은 달성할 수 없다

먼저 이것부터 정리해야 한다. **어떤 방식이든 원본에 표시를 남긴다.**

```
기능 플래그        원본 파일에 가드 한 줄
@Profile("!dr")   원본 컨트롤러에 애노테이션
컴포넌트 스캔 제외   원본 설정 파일에 제외 규칙
장기 브랜치        원본 파일이 브랜치에서 수정된다 (같은 diff, 위치만 다름)
소스 분리          포크. 원본이 둘이 된다
```

**`dr/mvp` 도 같은 파일을 같은 만큼 고친다.** diff 가 main 에 없을 뿐, 이미지를 뽑는
시점에는 반드시 적용된다. 그래서 질문이 "수정하나 안 하나" 가 아니다.

> **진짜 질문: 수정이 얼마나 크고, 한곳에 모이고, 되돌릴 수 있나. 그리고 그 수정이
> 검증되는가.**

---

## 2. 수정의 실제 크기

`apps/web` 은 **0 이다.** PR #40 이 지적한 두 대상 중 하나가 이미 없다.

```
aiFeatures.ts               삭제됨 (더 이상 필요 없다)
AIReport·Diagnosis 조건부     제거됨 (버튼은 DR 에서도 보인다)
Dockerfile ARG              제거됨 (빌드 인자 0)
```

DR 여부를 프론트가 알 필요가 없어졌기 때문이다. 서버가 503 과 문구로 답한다.

`apps/api` 는 파일 7개에 남는다. **주석을 빼면 파일당 1~5줄이다.**

| 파일 | 실질 코드 |
|---|---|
| `ArangoConfig` | `import` 1 + 애노테이션 1 |
| `ValidationRabbitConfig` | `import` 1 + 애노테이션 1 |
| `ValidationJobResultConsumer` | `import` 1 + 애노테이션 1 |
| `AgentServiceImpl` | `import` 1 + 필드 1 + 생성자 1 + 대입 1 + 호출 1 |
| `AgentDocumentServiceImpl` | 같은 형태 |
| `RadiologyReportServiceImpl` | 같은 형태 |
| `RadiologyReportController` | 같은 형태 |

애노테이션은 한 줄이다.

```java
@ConditionalOnProperty(name = "features.ai.enabled", havingValue = "true", matchIfMissing = true)
```

가드도 한 줄이다.

```java
aiFeatures.requireEnabled();
```

**DR 을 아는 지식은 전부 `AiFeatures.java` 한 파일에 있다.** 나머지 7개는 그 이름을
부르기만 한다. 실제로 PR #40 이 기계적으로 되돌릴 수 있었던 것이 그 증거다.

## 3. 판정 기준 넷

어떤 DR 방식이든 이 넷을 통과해야 한다.

### 기준 1 — 전체 스택 동작이 바뀌지 않는가

기본값이 켜짐(`matchIfMissing = true`, `${features.ai.enabled:true}`)이라 값을 주지
않으면 아무것도 달라지지 않는다.

**양쪽 다 통과한다.** `dr/mvp` 커밋 메시지도 같은 말을 한다.

### 기준 2 — DR 지식이 한곳에 모이는가

`AiFeatures.java` 하나다. 다른 파일은 그 이름만 부른다.

**양쪽 다 통과한다.** 같은 코드다.

### 기준 3 — 되돌릴 수 있는가

PR #40 이 실제로 되돌렸다. 파일 17개, 752줄, 충돌 없이.

**양쪽 다 통과한다.**

### 기준 4 — 그 수정이 검증되는가

**여기서 갈린다.**

```
플래그    main 에 있다. CI 가 매 푸시마다 DR 스택을 세워 확인한다
브랜치    main 에 없다. 이미지를 뽑을 때만. 그 사이는 아무도 안 본다
```

`dr/mvp` 는 이 위험을 스스로 적어 놨다.

> main 을 따라가지 못하면 DR 이미지가 조용히 낡는다. 오늘 certificate-api 이미지가
> 커밋 11개 뒤진 채 healthy 로 돌던 것과 같은 함정이다 — 낡은 코드가 정상 동작할
> 뿐이라 증상으로 드러나지 않는다.

**그 위험이 오늘 실제로 나타났다.**

## 4. 오늘 잡힌 것 — 기준 4 의 증거

DR 스택을 실제로 세워 X-ray 를 부르니 이랬다.

```
dr X-ray  500
{"error":"영상 판독 처리 중 오류가 발생했습니다: 503 SERVICE_UNAVAILABLE ..."}
```

원인 둘이었다.

**첫째, 503 이 500 으로 감싸졌다.** `processRadiologyReport` 의 마지막
`catch (Exception e)` 가 `ResponseStatusException` 도 잡아 다시 던진다. 컨트롤러에
분기가 있는데도 그 앞에서 삼켜졌다.

**문구는 문자열 안에 남아 살아남는다.** 화면에는 그럴듯한 안내가 뜨는데 상태 코드만
틀린 상태다 — 눈으로 봐서는 알 수 없다.

**둘째, 게이트 앞에서 이미 쓰기가 일어났다.** `uploadAndAnalyze` 는 판독 요청을 DB 에
저장하고 이미지를 디스크에 쓴 뒤에야 엔진을 부른다. 가드는 엔진 쪽에만 있었다.

```
radiology_report  id=2 patient_id=1 status=pending
/app/BitComputer/images/2/original/probe.jpg
```

DR 에서 버튼을 누를 때마다 고아 레코드와 이미지가 쌓인다. 코드 주석은 그 자리가
"진입점" 이라 그런 일이 없다고 적혀 있었는데, 그 진입점이 저장보다 뒤였다.

**이 둘은 `dr/mvp` 에도 그대로 있다.** 같은 코드이기 때문이다.

> **핵심은 이거다.** 이것들은 **DR 스택을 세워 봐야만** 드러난다. main 에서 AI 를 켜고
> 도는 한 영원히 안 보인다. 장기 브랜치에서는 **이미지를 뽑는 날 — 즉 재해가 난 날 —**
> 처음 드러난다.

## 5. 결정

**기능 플래그로 간다.**

기준 1~3 은 무승부다. **기준 4 가 유일한 차이이고, 오늘 그 차이가 결함 둘로 나타났다.**

`dr/mvp` 가 지불하려던 대가는 "main 이 깨끗하다" 인데, 그 대가로 얻는 것이 없다 —
수정은 이미지를 뽑는 시점에 어차피 적용되므로 사라지지 않고, 위치만 옮겨진다. 옮겨진
곳에서는 검증되지 않을 뿐이다.

### 대신 지키는 것

원본에 남는 수정을 최소로 묶는다.

- [ ] DR 지식은 `AiFeatures.java` 밖으로 나가지 않는다. 다른 파일은 그 이름만 부른다
- [ ] 원본 파일에 들어가는 것은 **애노테이션 한 줄 또는 가드 한 줄**뿐이다. `if (dr)` 로
      갈리는 로직 분기를 넣지 않는다
- [ ] 기본값은 항상 켜짐이다. 값이 없을 때 꺼지면 설정 실수가 DR 구성과 구별되지 않는다
- [ ] 프론트에는 DR 을 아는 코드를 두지 않는다. 서버가 503 과 문구로 답한다
- [ ] CI 의 `dr stack` 잡을 유지한다. **이것이 기준 4 를 지키는 유일한 장치다**

### `dr/mvp` 는 어떻게 하나

**병합하지 않고 삭제한다.** 담긴 752줄이 이 브랜치에 이미 있고, 남겨 두면 두 갈래가
생긴다 — 브랜치 방식이 피하려던 바로 그 문제다.

## 6. 곁가지로 정해진 것

기능 플래그를 프론트에서 걷어내면서 **프론트 이미지가 환경 무관해졌다.**

```
NEXT_PUBLIC_API_BASE_URL          상대 경로로 대체
NEXT_PUBLIC_AI_FEATURES_ENABLED   서버 503 문구로 대체
```

풀 스택과 DR 스택이 **같은 sha256 이미지**를 쓰는 것을 확인했다.

```
bit-frontend        bitcomputer-frontend:local     sha256:0ad7e145358b...
bit-dr-frontend     bitcomputer-frontend:local     sha256:0ad7e145358b...
bit-spring-boot     bitcomputer-spring-boot:local  sha256:daeef566ecba...
bit-dr-spring-boot  bitcomputer-spring-boot:local  sha256:daeef566ecba...
```

**이미지 7개, Deployment 8개. DR 이 추가하는 이미지는 0이다.**

전제가 하나 붙는다 — **프론트와 API 가 같은 호스트명 아래 있어야 한다.** AWS 는
CloudFront 가 그 조건을 만든다. **GCP DR 도 같은 구조여야 하고, 아니면 프론트
이미지가 다시 갈라진다.** 자세한 것은 [10 §7.2](10-aws-deployment-design.md) 에 있다.
