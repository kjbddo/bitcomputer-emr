# B1 — 런타임 검증층 설계

**작성일:** 2026-08-29
**상태:** 설계 승인됨
**선행:** B0(LLM 게이트웨이 통합, `2026-08-28-llm-gateway-design.md`) 완료

---

## 1. 배경 — B0 가 답하지 않은 질문

B0 는 한 가지를 했다. **LLM 없이 돌았을 때 그 사실을 숨기지 않게** 만들었다.

이전에는 LLM 이 없거나 실패하면 세 서비스가 각자 하드코딩 휴리스틱으로 조용히 떨어졌고, UI 는 그 출력을 모델이 만든 것처럼 보여줬다. 트레이스의 `thought` 문자열까지 하드코딩인데 사람이 읽으면 LLM 추론으로 보였다. 지금은 `llmStatus` 가 실행 경로에서 도출되고, 트레이스 각 스텝이 `source` 를 갖고, 의사 화면에 "규칙 기반 결과 — 모델 미사용" 배지가 뜬다.

**그러나 `llmStatus: "real"` 은 "모델이 돌았다"만 말한다.** 그 처방이 이 환자에게 적절한지, 그 진단서 문장이 실제 진료 기록과 맞는지는 시스템 어디에서도 확인하지 않는다. 모델이 완전히 틀린 처방을 자신 있게 내놓으면, 초록 배지와 함께 의사에게 그대로 간다.

B1 의 질문은 "모델이 돌았나"가 아니라 **"돈 결과가 조회한 데이터로 추적되나"** 다.

## 2. 기존 검증 자산에 대한 비판

이 설계는 백지에서 출발하지 않는다. `services/prescription/evals/` 와 `services/validation-agent/evals/` 에 LLM-as-judge 기반 오프라인 평가 하네스가 이미 있고, 그 안에 결정론적 휴리스틱도 있다. 다만 세 가지 이유로 그대로 승격할 수 없다.

**2.1 근거가 아니라 단어를 센다.**

`services/prescription/evals/metrics.py` 의 `heuristic_answer_quality` 는 `reason` 문자열에
`top_rx`, `유사`, `그래프`, `근거`, `데이터`, `코호트`, `입력` 중 하나가 들어 있으면 `reason_supported` 로 센다.
"데이터를 참고했습니다"라고 쓰면 근거가 전혀 없어도 통과하고, 실제로 잘 근거한 문장이 그 단어를 안 쓰면 실패한다.

**2.2 근거가 없을 때 검사가 스스로 꺼진다.**

같은 함수에서 `has_enough_top_rx` 가 false 이면(입력의 허용 처방이 3개 미만) `anchored += 1` 로 전부 통과시킨다. **입력이 빈약할 때가 모델이 지어낼 가능성이 가장 높은 순간인데 바로 그때 검사가 꺼진다.** 근거 부족을 안전 신호로 취급하는 것이 이 하네스의 가장 큰 결함이다.

부수적으로 `dosage` 검사에는 조용한 누락도 있다. 용량 문자열에 `mg`·`매`·`회` 중 어느 토큰도 없으면 증가도 이슈 기록도 없이 그냥 사라진다.

**2.3 할루시네이션 검사가 자기 시나리오의 함정만 찾는다.**

`heuristic_hallucination` 은 `"DB 저장 완료"`, `"PMID 99999999"`, `"슈퍼관절완치"` 같은 고정 문자열 목록을 본다. 이 문자열들은 `evals/generate_scenarios.py` 가 심은 함정이다. 즉 평가 하네스가 자기가 심은 것을 찾는 구조이고, 런타임에서는 무용하다.

**2.4 그리고 아무도 안 돌린다.**

`evals/results/` 의 최신 산출물이 2026-06-06 자다. `ci.yml` 에 eval 이 걸려 있지 않다. 그 사이 B0 가 세 서비스의 LLM 경로를 전부 갈아엎었다.

## 3. 범위

### 3.1 하는 것

각 서비스가 자기 출력의 각 주장이 **실제로 조회해온 데이터 안에 있는지** 결정론적으로 대조하고, 결과를 응답에 실어 의사 화면에 표시한다.

### 3.2 하지 않는 것

- **차단하지 않는다.** 표시만 한다. 응답은 그대로 나간다.
- **임상적 적절성을 판단하지 않는다.** 저장소에 약물 상호작용·금기·알레르기 지식 베이스가 없다(확인함). 지식 없이 적절성을 검증하는 척하면 이 프로젝트가 고치려는 문제를 검증층 안에서 반복한다. "실재하는 약인데 이 환자에게 틀린" 경우는 이 설계가 못 잡는다고 명시한다.
- **B(NLI)는 이 스펙에 설계로 포함하되 마지막 단계다.** 기본이 `off` 이고 A 와 독립적으로
  출시할 수 있다. A 가 표시 표면을 먼저 확정하므로 B 는 그 위에 검사만 추가하는 형태가 된다.
- **오프라인 평가 하네스를 고치지 않는다.** §2 의 비판은 기록으로 남기되, 하네스 재건은 B1 의 후속(별도 스펙)이다.
- **`validation-agent` 의 기존 `checks[]` 를 건드리지 않는다.** 그것은 도메인 검증(상병-처방 정합성)이고 의미가 다르다.

### 3.3 대조에 쓸 수 있는 데이터

| 서비스 | 조회 결과로 가진 것 |
|---|---|
| prescription | `top_rx`(실제 방문 처방 라인), Arango 후보, 코호트 요약 |
| certificate | 상병코드·처방코드·처방명으로 만든 premise |
| validation-agent | PubMed 관측값(PMID 포함), prescription finder 관측값 |

## 4. 아키텍처

각 서비스에 **순수 함수 모듈**을 하나씩 둔다. I/O 없음, LLM 없음.

```
services/prescription/verification.py               (prescription_api 용)
services/prescription/certificate_verification.py   (certificate_api 용)
services/validation-agent/app/verification.py
```

시그니처는 세 곳 모두 같은 형태다.

```python
def verify(*, context: Context, output: Output) -> VerificationResult
```

**4.1 검증기는 요청이 아니라 조회 결과를 받는다.**

`PrescriptionRecommendRequest` 를 넘기면 안 된다. 요청은 호출자가 주장하는 것이고, 검증은 서비스가 실제로 조회한 것에 대조해야 한다. Arango 조회 결과, PubMed 관측값, premise 필드를 넘긴다. 이 구분이 없으면 "요청에 적혀 있으니 근거 있음"이 되어 검증이 무의미해진다.

**4.2 순수 함수라 LLM 없이 테스트된다.**

현재 프로젝트에 유효한 LLM API 키가 없다. 검증기가 순수 함수이므로 키 없이 전부 만들고 검증할 수 있다. 이것이 A(결정론)를 B(NLI)보다 먼저 하는 실질적 이유다.

**4.3 출력을 변형하지 않는다.**

검증기는 판정만 반환한다. 처방·소견 내용에 손대지 않는다.

**4.4 호출 위치.**

각 서비스가 LLM 출력을 파싱한 뒤, 응답 객체를 조립하기 전에 부른다. 검증 실패가 본 응답을 실패시키면 안 된다 — 검증기에서 예외가 나면 `status="skipped"`, `skippedReason` 에 예외 타입을 남기고 진행한다.

## 5. 검증 결과 계약

```python
CheckOutcome = Literal["ok", "flagged", "skipped"]


@dataclass(frozen=True)
class CheckResult:
    id: str            # "code_in_candidates", "dosage_verbatim", ...
    target: str        # 어느 항목인지: "prescription[1]", "sentence[3]"
    outcome: CheckOutcome
    evidence: str      # 왜 그렇게 판정했는지, 사람이 읽는 한 줄


@dataclass(frozen=True)
class VerificationResult:
    status: Literal["passed", "flagged", "skipped"]
    checks: List[CheckResult]
    skippedReason: Optional[str] = None
```

**5.1 `status` 는 실행 경로에서 도출한다.**

설정이나 "검사를 켰는가"가 아니라 실제로 무엇이 실행됐는가에서 나온다. 집계 규칙:

검사를 두 부류로 나눈다.

- **구조 검사**: 출력 자체의 형태만 본다. 조회 데이터가 필요 없다.
  (`schema_top3`, `confidence_in_range`)
- **근거 검사**: 조회 데이터와 대조한다. 나머지 전부.

집계:

- 검사 중 하나라도 `flagged` → `"flagged"`
- `flagged` 가 없고 **근거 검사** 중 `ok` 가 하나 이상 → `"passed"`
- 그 외 → `"skipped"`

**구조 검사만 통과한 것으로는 `"passed"` 가 되지 않는다.** 형식이 맞다는 것과
근거가 있다는 것은 다른 말이고, 둘을 합치면 §2.2 의 결함이 다른 모양으로
돌아온다 — 조회 데이터가 하나도 없어도 rank 가 1,2,3 이기만 하면 "검증됨"이
뜬다. 검사가 하나도 없는 경우(빈 목록)도 같은 규칙으로 `"skipped"` 다.

B0 에서 `llmStatus` 를 두 번 틀렸던 지점이다. 한 번은 환경변수를 읽어서, 한 번은 보조 호출의 성공을 결정 소스에 섞어서. 여기서는 집계 입력이 이 요청에서 실제로 실행된 검사 결과뿐이다.

**5.2 `"skipped"` 가 별도 값인 것이 이 설계의 중심이다.**

§2.2 의 결함을 정면으로 고친다. **대조할 근거가 없으면 `"passed"` 가 아니라 `"skipped"`** 이고 `skippedReason` 에 왜인지 남긴다. 근거 부족은 안전 신호가 아니라 미확인 신호다.

**5.3 응답 필드명은 `verification`.**

`validation-agent` 의 기존 `checks[]` 와 이름이 비슷하나 다른 것이다. 기존 필드는 건드리지 않는다.

**5.4 Java DTO 를 함께 넓힌다.**

B0 의 Task 10·11 에서 확인된 함정이다. `@JsonIgnoreProperties(ignoreUnknown = true)` 가 붙은 DTO 는 모르는 필드를 조용히 버린 뒤 재직렬화한다. `verification` 을 추가할 때 `ValidationAgentResponse`, `CertificateAgentResponse`, `GenerateCertificateResponseDTO` 를 같은 변경에서 넓히지 않으면 필드가 저장 전에 사라진다. **파이썬 쪽 필드 추가와 Java DTO 확장은 한 태스크 안에서 같이 한다.**

## 6. 서비스별 검사 목록

### 6.1 prescription

| id | 무엇을 대조하나 | 근거 없으면 |
|---|---|---|
| `schema_top3` | 항목 3개, rank 가 정확히 {1,2,3}, 코드 중복 없음 | — (항상 판정 가능) |
| `code_in_candidates` | 각 `prescription_code` 가 조회된 후보 집합에 있는가 | `skipped` |
| `name_matches_code` | 후보 집합에서 그 코드에 붙은 이름과 반환된 `name` 이 같은가 | `skipped` |
| `dosage_verbatim` | `dosage` 가 해당 코드의 원본 처방 라인에 문자 그대로 나오는가 | `skipped` |
| `confidence_in_range` | `confidence_score` 가 0..1 범위인가 | — |

**`reason` 검사는 A 에서 뺀다.** §2.1 의 `reason_supported` 를 이식하지 않는다. 산문으로 쓰인 이유의 타당성은 결정론적으로 판정할 수 없고, 단어 존재로 대신하는 순간 이 프로젝트가 고치려는 문제를 반복한다. 이유의 근거성은 B(NLI)가 할 일이고, 그때까지는 검증하지 않는다고 정직하게 둔다.

`dosage_verbatim` 이 §2.2 의 조용한 누락을 고치는 지점이다. 원본 라인에 용량 정보가 없으면 `skipped` 로 남긴다.

### 6.2 certificate

| id | 무엇을 대조하나 | 근거 없으면 |
|---|---|---|
| `cited_code_known` | 소견에 ICD-10 형태 토큰(`[A-Z]\d{2}(\.\d+)?`)이 있으면 premise 의 상병코드 중 하나인가 | `skipped` |
| `premise_term_present` | 상병명·처방명 중 최소 하나가 소견에 나타나는가 | `skipped` |

진단서는 자유 산문이라 A 로 얻는 것이 얇다. 결정론적으로 잡히는 것은 "없는 상병코드를 인용했다"와 "근거로 삼았다는 상병을 한 번도 언급하지 않았다" 정도다.
코드 형태는 ICD-10 정규식으로 고정한다 — "코드처럼 생긴 것"을 애매하게 두면 검사가 무엇을 하는지 아무도 모른다. **진단서가 B 의 주 수혜자**이며, `CertificateEvaluationServiceImpl` 에 이미 NLI 구현이 있어 플래그를 켜면 가장 먼저 값이 붙는다.

빈 본문·비문자열 `content` 는 B0 Task 8 에서 이미 502 가드로 막았다. 검사로 중복하지 않는다.

### 6.3 validation-agent

| id | 무엇을 대조하나 | 근거 없으면 |
|---|---|---|
| `cited_pmid_in_evidence` | 요약·checks 에 등장하는 모든 PMID 가 PubMed 관측값에 실재하는가 | `skipped` |
| `candidates_from_finder` | `candidatePrescriptions` 가 전부 finder 관측값에서 왔는가 | `skipped` |
| `trace_step_has_observation` | 트레이스 각 스텝이 비어 있지 않은 `observation` 을 갖는가 | — |

`cited_pmid_in_evidence` 가 세 서비스 통틀어 가장 강한 검사다. PMID 는 식별자라 대조가 명확하고, 지어낸 논문 인용은 의료 맥락에서 가장 위험한 할루시네이션 부류다. §2.3 이 고정 문자열 하나를 찾던 자리에 실제 집합 대조가 들어간다.

`trace_step_has_observation` 은 약하지만 명확하다. 관측값이 없는 스텝은 기록 없는 주장이다.
"주장이 관측값에 대응하는가" 같은 넓은 문구는 쓰지 않는다 — 구현자마다 다르게 읽고,
무엇을 검증하는지 아무도 말할 수 없는 검사가 된다.

## 7. 표시

**7.1 `llmStatus` 배지 옆에 배지를 더 붙이지 않는다.**

B0 Task 11 리뷰에서 `overallStatus` 가 `WARNING` 일 때 amber 배지 둘이 나란히 서서 어느 쪽이 판정이고 어느 쪽이 출처인지 구분이 안 되는 문제가 나왔다. `llmStatus` 는 "모델이 돌았나", `verification` 은 "출력이 조회 데이터로 추적되나" — 축이 다른 신호를 같은 모양으로 쌓으면 둘 다 안 읽힌다.

**7.2 항목 단위로 표시한다.**

처방 3건 중 1건만 근거가 없으면 그 행에 표시한다. 전역 배지 하나로 뭉치면 어느 처방이 문제인지 알 수 없고, 그건 표시하지 않는 것과 크게 다르지 않다.

| 서비스 | 위치 |
|---|---|
| prescription | 추천 표의 각 행 + 표 위 요약 한 줄("3건 중 1건 미검증") |
| certificate | AI 미리보기 모달의 소견 텍스트 위 한 줄 |
| validation-agent | 검증 이유 목록의 해당 항목 |

**7.3 `flagged` 와 `skipped` 를 다른 문구로 쓴다.**

- `flagged` → "근거 불일치"
- `skipped` → "미검증"

"근거와 어긋난다"와 "대조할 근거가 없었다"는 의사에게 다른 정보다. 하나로 뭉치면 신호가 희석된다 — B0 Task 6 에서 완벽한 LLM 요청도 매번 `fallback` 항목을 뱉어 표시를 무시하게 됐던 것과 같은 실패다.

**7.4 fail-closed.**

`verification` 필드가 없거나 값이 계약 밖이면 "검증됨"이 아니라 "미검증"으로 렌더한다. `apps/web/src/utils/llmStatus.ts` 의 `llmStatusNotice` 와 같은 방향이며, 같은 파일에 나란히 둔다.

## 8. B(NLI) 플래그

```
LLM_VERIFICATION_NLI=off        # off | on, 기본 off
```

**8.1 게이트웨이를 통해 호출한다.** 직접 호출하지 않는다. 자격증명이 게이트웨이에만 있다는 성질(B0 spec §3.1)이 검증층에도 적용된다.

**8.2 `X-LLM-Caller` 를 분리한다.** `prescription-api-nli`, `certificate-api-nli`, `validation-agent-nli`. 계측이 검증 비용을 본 기능 비용과 따로 집계한다. B 를 기본으로 켤지 판단하려면 그 숫자가 필요하다.

**8.3 NLI 결과도 fail-closed.** 2차 호출이 실패하면 해당 검사는 `skipped` 이고 절대 `ok` 가 아니다. 검증기가 자기 실패를 통과로 바꾸면 검증층이 있는 이유가 사라진다.

**8.4 별도의 짧은 예산을 갖는다.**

현재 타임아웃 사다리는 게이트웨이 총예산 136.5초 < 호출자 180초다(B0 최종 리뷰에서 정렬함). NLI 2차 호출이 붙으면 한 요청에 게이트웨이 호출이 둘이 되어 최악 273초가 되고 사다리가 뒤집힌다.

따라서 NLI 호출은 **30초, 재시도 없음**의 별도 예산을 갖고, 초과하면 `skipped` 로 떨어진다. 본 응답이 검증 때문에 지연되거나 실패하면 안 된다. 환경변수 `LLM_VERIFICATION_NLI_TIMEOUT_SECONDS=30`.

**이 30초는 요청 하나에 대한 총 예산이지, 검사하는 문장마다 새로 지급되는 예산이 아니다.** 소견은 문장 단위로 쪼개져 문장마다 독립된 게이트웨이 호출을 하나씩 만든다(§6.2) — 이 예산을 문장마다 다시 적용하면 N 문장에서 최악이 136.5 + 30×N 이 되어 사다리가 다시 뒤집힌다(실제로 소수점이 포함된 평범한 세 문장짜리 소견도 문장 분리기가 잘못 다루면 네 조각까지 늘어난 사례가 있었다). 구현은 호출 시작 시점에 마감(deadline)을 한 번만 잡고, 이미 마감을 넘긴 문장은 게이트웨이를 아예 호출하지 않고 `skipped` 로 떨어뜨려 총 지연을 30초 안에 묶는다.

## 9. Global Constraints

이 스펙에서 파생되는 모든 태스크에 적용된다.

- **GC-1: 검증기는 순수 함수다.** I/O·LLM·전역 상태를 쓰지 않는다. A 단계에서 예외 없음.
- **GC-2: 근거 없음은 통과가 아니다.** 대조할 데이터가 없으면 `skipped`. `passed` 로 떨어지는 경로를 만들지 않는다.
- **GC-3: 검증기는 출력을 변형하지 않는다.**
- **GC-4: 검증 실패가 본 응답을 실패시키지 않는다.** 검증기 예외는 `skipped` 로 흡수한다.
- **GC-5: 상태는 실행 경로에서 나온다.** 설정이나 플래그 값에서 도출하지 않는다.
- **GC-6: 기존 필드를 건드리지 않는다.** `llmStatus`, `engineStatus`, `checks[]`, `reasoningTrace[].source` 모두 그대로 둔다.
- **GC-7: 파이썬 필드 추가와 Java DTO 확장은 같은 태스크에서 한다.** §5.4 참조.
- **GC-8: 각 검사는 그것을 지웠을 때 빨개지는 테스트를 갖는다.** §10 참조.

## 10. 테스트 전략

순수 함수라 표 기반 테스트로 전부 덮인다. LLM 도 I/O 도 필요 없다.

**10.1 검사마다 변이 테스트.**

각 검사를 지우거나 무력화했을 때 빨개지는 테스트가 있어야 한다. 이 프로젝트에서 리뷰어가 반복해서 찾아낸 것이 "지워도 스위트가 초록인 검사"였다 — B0 Task 7 에서 8개, Task 8 에서 13개. 검증층에서는 특히 치명적이다. **검증이 조용히 죽으면 화면에는 계속 "검증됨"이 뜬다.**

**10.2 근거 없음이 `passed` 가 되지 않는다는 음성 대조.**

빈 컨텍스트를 주고 `skipped` 가 나오는지 확인하고, `passed` 를 반환하도록 변이시켰을 때 테스트가 빨개지는지 확인한다.

**10.3 검증기가 출력을 변형하지 않는다는 테스트.**

입력 객체를 검증 전후로 비교한다.

**10.4 웹 표시의 fail-closed 테스트.**

필드 누락 / `null` / 계약 밖 값 / 대소문자 불일치 네 가지 shape 를 렌더 경로로 구동해, 어느 것도 "검증됨"으로 렌더되지 않는지 확인한다.

## 11. 실측이 필요한 항목

- [ ] `code_in_candidates` 의 실제 flagged 비율. 0% 면 검사가 무의미하거나(모델이 절대 지어내지 않음) 후보 집합이 너무 넓다는 뜻이다. 100% 에 가까우면 후보 집합 구성이 틀렸다.
- [ ] `skipped` 비율. 높으면 검증층이 이름만 있고 실제로는 대부분 판정하지 못한다는 뜻이다. 그 경우 조회 데이터를 더 확보하는 것이 먼저다.
- [ ] NLI 2차 호출의 요청당 추가 비용과 지연. `X-LLM-Caller` 분리로 계측된다. 이 숫자 없이 B 를 기본으로 켜지 않는다.
- [ ] 30초 NLI 예산이 실제 응답 시간 대비 충분한가. B0 spec §10.2 의 45초 항목과 같이 측정한다.

## 12. 완료 조건

1. 세 서비스가 각각 `verification` 을 응답에 싣는다.
2. `verification.status` 가 실행 경로에서 도출되며, 근거가 없을 때 `passed` 가 되는 경로가 없다.
3. Java DTO 세 개가 `verification` 을 보존하고, 동기·비동기 경로 모두에서 저장된다.
4. 의사 화면 세 곳에 항목 단위 표시가 뜨고, `flagged` 와 `skipped` 가 다른 문구로 구분된다.
5. 필드 누락 / `null` / 계약 밖 값이 "검증됨"으로 렌더되지 않는다.
6. 각 검사에 대해 그것을 무력화했을 때 빨개지는 테스트가 존재한다(변이 표로 증명).
7. `LLM_VERIFICATION_NLI=off` 가 기본이고, 켰을 때 별도 `X-LLM-Caller` 로 계측된다.
8. NLI 호출이 실패·타임아웃해도 본 응답이 성공하며 해당 검사가 `skipped` 로 남는다.
9. §11 의 미확인 항목이 측정되고 결과가 이 문서에 기록된다.
