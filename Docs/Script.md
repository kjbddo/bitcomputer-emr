# 최종발표 스크립트

## 발표 시작

안녕하세요. 저희 팀 **슈붕보다팥붕**은 “Anomaly Detection Model 기반 XAI Agent 시스템”을 주제로 프로젝트를 진행했습니다.

본 프로젝트의 핵심 목표는 X-ray 영상 분석 결과와 환자 진료 데이터를 연결하고, 이를 기반으로 설명 가능한 처방 추천 및 검증 시스템을 구현하는 것입니다. 발표는 프로젝트 배경, 요구분석, 시스템 설계, 주요 구현사항, 성능 평가, 시연, 기대효과 순서로 진행하겠습니다.

---

## 1. 프로젝트 배경

먼저 프로젝트 배경입니다.

의료 현장에서는 X-ray와 같은 영상 판독 결과가 존재하더라도, 이를 실제 처방 추천이나 처방 검증 로직으로 직접 연결하는 데 어려움이 있습니다. 단순히 영상에서 이상 소견을 찾는 것만으로는 충분하지 않고, 해당 결과가 환자의 상병, 증상, 처방과 어떻게 연결되는지 설명할 수 있어야 합니다.

또한 AI가 추천한 처방을 의료진이 신뢰하기 위해서는 “왜 이 처방이 추천되었는가”에 대한 근거가 필요합니다. 따라서 저희는 단순 추천 모델이 아니라, 추천 근거와 검증 과정을 함께 제공하는 설명 가능한 AI, 즉 XAI 기반 에이전트 시스템을 설계했습니다.

---

## 2. 요구분석

다음은 요구분석입니다.

프로젝트를 진행하면서 몇 가지 제한사항이 있었습니다. 첫째, 실제 의료 영상 데이터는 접근 권한 문제로 직접 사용할 수 없었기 때문에, 공개 데이터와 시뮬레이션 가능한 구조를 기반으로 시스템을 구성했습니다. 둘째, LLM 기반 시스템은 환각, 즉 존재하지 않는 약물명이나 처방코드를 생성할 위험이 있으므로 이를 검증하는 로직이 필요했습니다. 셋째, 영상 분석, 처방 추천, 검증 과정이 모두 포함되기 때문에 실시간 사용 시 네트워크 지연 시간도 고려해야 했습니다.

이에 따라 요구사항은 크게 네 가지로 정리했습니다. X-ray를 비롯한 환자 정보 기반 처방 3순위 추천, 추천 근거와 신뢰도 점수 제공, LLM 환각 방지를 위한 검증 로직, 그리고 피드백 기반 추천 재보정 및 진단서 자동 생성 기능입니다.

---

## 3. 프로젝트 주제 및 개념설계

저희 프로젝트의 주제는 **Anomaly Detection Model 기반 XAI Agent 시스템**입니다.

개념적으로는 의료 영상 분석부터 처방 추천, 검증, 진단서 생성까지 이어지는 End-to-End 에이전트 시스템을 목표로 했습니다. X-ray 이미지에서 이상 부위를 탐지하고, 유사 사례를 검색해 상병 후보를 추론한 뒤, 환자 컨텍스트와 상병 정보를 기반으로 처방 후보를 추천합니다.

여기서 중요한 점은 추천 결과를 그대로 사용하는 것이 아니라, ArangoDB 기반 그래프 근거와 ValidationAgent의 검증 결과를 함께 제공한다는 점입니다. 이를 통해 의료진이 AI 결과를 참고하되, 최종 판단은 의료진이 수행하는 구조로 설계했습니다.

## 4. 통합 아키텍처

다음은 전체 시스템 아키텍처입니다.

프론트엔드는 Next.js 기반으로 구현했고, 사용자는 웹 UI에서 환자 접수, 진료실, 처방 추천, 진단서 생성 기능을 사용할 수 있습니다. 백엔드는 Spring Boot로 구성하여 환자, 진료 이력, 상병, 처방, 진단서 데이터를 관리합니다.

AI 서비스는 Python FastAPI 기반으로 분리했습니다. 처방 추천 API, X-ray 분석 서비스, 진단서 생성 API, ValidationAgent가 각각 독립적으로 동작합니다. MySQL은 병원 업무 데이터를 저장하고, ArangoDB는 방문-상병-처방 관계를 그래프 형태로 저장해 처방 추천 근거로 활용합니다.

또한 RabbitMQ를 사용하여 처방 추천 이후 검증 작업을 비동기로 처리했습니다. 이 구조를 통해 사용자 요청과 검증 에이전트 실행을 분리하고, 검증 과정이 길어져도 시스템 응답성을 유지할 수 있도록 했습니다.

## 5. 처방 추천 상세 설계

처방 추천은 ArangoDB 그래프를 기반으로 설계했습니다.

그래프에는 환자의 방문 정보, 상병 정보, 처방 정보가 연결되어 있습니다. 추천 API는 현재 환자와 상병 코드를 입력받고, 해당 상병과 과거 처방 사이의 co-occurrence 관계를 조회합니다. 또한 유사 환자군에서 자주 등장한 처방 패턴을 분석하여 추천 후보를 구성합니다.

이후 LLM은 단순히 임의의 처방을 생성하는 것이 아니라, ArangoDB에서 조회된 처방 후보와 환자 증상, 진료 이력을 기반으로 Top-3 처방을 JSON 형태로 반환합니다. 추천 결과에는 처방명, 처방코드, 추천 사유, 신뢰도 점수가 포함됩니다.

---

## 6. X-ray 이상 탐지 및 상병 추론 파이프라인

다음은 X-ray 이미지 기반 상병 추론 파이프라인입니다.

먼저 환자의 X-ray 이미지가 입력되면 anomaly detection 모델이 흉부 영역 내 이상 부위를 탐지합니다. 이후 탐지된 병변 후보 영역을 중심으로 ROI 마스킹을 수행하여 불필요한 배경 정보를 줄이고, 병변의 시각적 특징을 강조합니다.

그 다음 마스킹된 이미지를 임베딩 벡터로 변환합니다. 이 벡터는 기존 X-ray Vector DB의 이미지 임베딩과 유사도 비교를 수행하는 데 사용됩니다. 유사도가 높은 과거 케이스를 검색하고, 해당 케이스의 진단 이력을 참고하여 의심 상병 후보를 도출합니다.

결과적으로 이 모듈은 진단을 확정하는 기능이 아니라, 영상 기반 의심 상병과 시각적 근거를 제공하여 의료진의 판단을 보조하는 역할을 합니다.

## 7. 신뢰도 기반 XAI 처방 추천

처방 추천 결과에는 confidence_score를 함께 제공합니다.

이 점수는 LLM이 자체적으로 만든 점수가 아니라, ArangoDB 그래프 관계와 의사 피드백 이력을 결합해 계산합니다. 입력 데이터는 현재 진료 상병 데이터와 ArangoDB의 상병-처방 co-occurrence 이력입니다.

계산 로직은 크게 Frequency Score와 Similarity Score로 구성됩니다. Frequency Score는 동일 상병 코드에서 특정 처방이 얼마나 자주 등장했는지를 나타내고, Similarity Score는 유사 환자군 또는 유사 상병 케이스에서 해당 처방이 얼마나 관련 있는지를 반영합니다.

또한 의사가 추천을 수용했는지, 거부했는지, 또는 AI가 놓친 처방을 직접 추가했는지를 피드백으로 저장합니다. 이 accepted, rejected, missed 피드백은 이후 추천 점수 보정에 활용됩니다.

---

## 8. 처방 추천 검증 및 재추천

다음은 처방 추천 결과를 검증하는 구조입니다.

처방 추천 요청이 발생하면 Spring Boot는 환자 정보, 저장 상병, 저장 처방, 최신 X-ray 추론 결과를 모아 Validation Job을 생성합니다. 이 Job은 RabbitMQ를 통해 ValidationAgent로 전달됩니다.

ValidationAgent는 ReAct 기반 reasoning loop를 수행하면서 필요한 도구를 선택합니다. 예를 들어 X-ray Result Loader는 영상 추론 결과를 불러오고, Disease Validator는 저장 상병과 X-ray 추론 결과의 일관성을 확인합니다. Prescription Validator는 처방과 상병, 증상 간의 관련성을 검토하고, PubMed Evidence Loader는 필요한 경우 문헌 근거를 검색합니다.

최종적으로 Agent는 검증 상태, 검증 이유, reasoning trace, PubMed 근거, 추천 처방 후보를 JSON 형태로 반환합니다. 이 결과는 프론트엔드에서 모달로 표시되어, 의사가 AI 추천 결과를 한 번 더 검토할 수 있도록 합니다.

## 9. 진단서 자동 생성

보조 기능으로 진단서 자동 생성 기능을 구현했습니다.

진단서 생성 API는 환자 정보, 상병, 처방, 의사 소견을 입력으로 받아 한국어 의학 소견을 생성합니다. 진단서 종류는 일반 소견과 군 입대용 제한 평가를 포함한 템플릿으로 나누어 구성했습니다.

생성된 진단서는 의료진이 화면에서 직접 수정할 수 있으며, 수정된 내용은 PDF로 저장하거나 DB에 저장할 수 있습니다. PDF 저장 과정에서는 `html2canvas`와 `pdf-lib`를 활용해 출력 품질을 확보했습니다.

## 10. 기타 EMR 기능

그 외에도 병원 업무를 지원하기 위한 EMR 기능을 구현했습니다.

보안 측면에서는 JWT 기반 인증과 권한 제어를 적용했습니다. 관리자 계정은 직원 계정 관리가 가능하고, 의사, 간호사, 원무과 직원은 각 역할에 맞는 화면과 기능만 사용할 수 있도록 구성했습니다.

## 11. 성능 평가: 데이터셋 구성

다음은 성능 평가입니다.

처방 추천 성능 평가는 Train Set, Calibration Set, Validation & Test Set으로 나누어 진행했습니다. Train Set은 기저 통계 생성에 사용했고, Calibration Set은 파라미터와 임계값 조정에 사용했습니다. Validation & Test Set은 최종 평가용으로 분리하여 튜닝에 사용하지 않았습니다.

데이터 규모는 Train Set 746 방문, 5,991 처방 행, Calibration Set 160 방문, 995 처방 행, Validation & Test Set 161 방문, 1,220 처방 행으로 구성했습니다.

## 12. 성능 평가: 처방 추천 정확도

처방 추천 적정성 분류 결과입니다.

Test Set 기준으로 Appropriate는 954건, 78.2%로 나타났고, Needs Review는 96건, 7.9%, Insufficient Data는 170건, 13.9%였습니다.

Calibration AUC는 0.860으로 측정되었고, Decision Threshold는 0.00737로 설정되었습니다. 이 결과는 그래프 기반 통계 점수가 실제 처방 적정성 판단에 일정 수준의 구분력을 가진다는 점을 보여줍니다.

## 13. 성능 평가: 에이전트 Tool 호출 정확도

다음은 에이전트 성능 평가 결과입니다.

이번 에이전트 평가는 세 가지 축, 즉 Tool 호출 정확도, 답변 퀄리티, 할루시네이션으로 나누어 진행했습니다. 먼저 Tool 호출 정확도는 입력 조건에 따라 필요한 파이프라인 단계가 실제로 실행되었는지를 보는 평가입니다.

여기서 Tool은 ReAct Agent의 자유로운 도구 선택이 아니라, DB 조회, confidence score 계산, 프롬프트 생성, LLM 생성, JSON 파싱 같은 조건부 파이프라인 단계를 의미합니다. 평가에는 정상 케이스, 희소 데이터, 공격 프롬프트, hallucination trap을 포함한 총 50개 케이스를 사용했습니다.

각 케이스마다 기대되는 Tool path와 실제 `toolTrace`를 비교했고, Precision과 Recall의 조화평균인 F1 Score로 최종 성능을 계산했습니다. 최종 F1 Score는 0.924로, 전체 파이프라인 호출 흐름은 매우 안정적으로 작동했습니다.

Tool별로 보면 `llm_generate`는 F1 1.0으로 LLM 생성 단계가 안정적으로 실행되었습니다. 반면 `confidence_scores`는 F1 0.4로 낮게 나왔는데, 이는 구현에서는 상병 코드가 있을 때 confidence를 넓게 계산하는 반면, judge 기준에서는 일부 케이스를 불필요 호출로 본 영향이 있습니다. 따라서 이 부분은 구현 오류라기보다는 평가 기준과 운영 정책을 더 명확히 맞출 필요가 있는 지점입니다.

## 14. 성능 평가: 에이전트 답변 퀄리티

다음은 답변 퀄리티 평가입니다.

답변 퀄리티는 에이전트가 반환한 Top-3 처방 추천이 JSON 출력 형식을 지키는지, 그리고 추천 내용이 입력 데이터, DB 조회 결과, 그래프 및 cohort 근거와 논리적으로 연결되는지를 확인했습니다.

평가 모델은 OpenAI `gpt-4o-mini`를 사용했고, 동일하게 총 50개 케이스를 대상으로 평가했습니다. 판단 기준은 출력 포맷 지침 준수 여부, 입력과 DB 결과 간의 연결성, 추천 사유가 실제 근거에 부합하는지 여부입니다.

잘 맞춘 케이스에서는 `top_rx` 안에 있는 처방명과 처방코드를 그대로 반영했고, cohort 근거를 추천 사유에 인용했으며, 입력에 존재하는 용량과 코드만 사용했습니다.

반대로 실패한 케이스에서는 추천 사유가 그래프나 cohort 근거를 충분히 인용하지 못하거나, 추천 처방코드가 실제 근거 데이터와 불일치하거나, 입력 또는 조회 결과에 없는 처방명을 추천하는 문제가 있었습니다.

최종 평균 relevance score는 0.386으로 낮게 측정되었습니다. 즉, JSON 형식 자체는 대체로 지켜졌지만, 추천 내용과 근거 데이터 간의 논리적 연결성은 아직 부족하다고 해석할 수 있습니다.

## 15. 성능 평가: 에이전트 할루시네이션

세 번째는 할루시네이션 평가입니다.

할루시네이션은 입력이나 DB 조회 근거에 없는 정보를 모델이 사실처럼 생성하는지를 확인하는 평가입니다. 예를 들어 입력에 없는 약물명이나 처방 횟수, 환자 정보를 생성하거나, 근거가 부족한데도 확정적으로 추천하거나, 공격 프롬프트 지시에 따라 특정 약을 무조건 추천하는 경우를 hallucination으로 보았습니다.

평가는 OpenAI `gpt-4o-mini` judge를 사용해 총 50개 케이스에 대해 수행했습니다. 그 결과 45개 케이스에서 hallucination이 발견되었고, hallucination rate는 0.900으로 측정되었습니다.

Control Group별로 보면 정상 입력인 `BASELINE_SAFE` 9개 중 4개에서도 일부 근거 밖 처방 생성이 확인되었습니다. 특히 `SPARSE_DATA` 9개에서는 9개 모두 hallucination으로 판정되었는데, 이는 근거가 부족한 상황에서 추천을 보류하지 못하고 약물명이나 코드, 용량을 채우려는 경향이 있었기 때문입니다.

따라서 이 결과는 현재 시스템에서 가장 중요한 개선 지점을 보여줍니다. 향후에는 입력과 DB 조회 근거 밖의 처방명과 처방코드를 차단하고, 근거가 부족할 경우 Top-3를 억지로 채우지 않고 “근거 부족” 또는 “추가 검토 필요”로 응답하는 가드레일을 강화해야 합니다.

## 16. 진단서 생성 성능 평가

진단서 생성 기능은 LLM이 생성한 소견과 실제 처방 간의 함의 관계를 기준으로 평가했습니다.

총 114건의 케이스에 대해 LLM-as-Judge 방식으로 평가했고, entailment rate는 79.36%로 측정되었습니다. 이는 생성된 소견이 실제 처방과 상당 부분 의미적으로 연결되어 있음을 보여주지만, 의료 문서 특성상 최종 문안은 반드시 의료진이 확인하고 수정할 수 있도록 설계했습니다.
